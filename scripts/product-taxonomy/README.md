# Багатомовний каталог товарів

Це перевірюваний набір класифікацій і інструменти підготовки до застосування.
`prepare.mjs` працює лише з файлами: він не під'єднується до БД і нічого в ній не
змінює. Архітектура — [ADR-0025](../../docs/decisions/0025-multilingual-product-taxonomy.md).

## Файли

- `catalog.json`: сімейства й варіанти; стабільні ID, три переклади та синоніми.
- `assignments.json`: рівно один запис на назву з вихідного inventory; поля
  класифікації, бренд, Bio та статус з поясненням сумнівів.
- `catalog-review.md`: згенерована читабельна таблиця всіх призначень для перегляду.
- `proposed-backfill.sql`: згенерований план запису лише `ready` відповідностей.
- `catalog-tools.mjs`: перевірка повноти, FK, дублів та генерація SQL.
- `verify-local.ps1`: інтеграційні SQL-тести на окремій тимчасовій PostgreSQL 17.

Статуси: `ready` — достатньо даних для призначення; `review` — потрібне уточнення;
`excluded` — службовий рядок, який не класифікується як товар. Уточнення роби в
JSON, потім повторно генеруй SQL. Не редагуй згенерований SQL вручну.

Для впізнаваних харчів без Bio/organic `is_organic=false` є погодженим робочим
припущенням; явний Bio дає `true`; незастосовна/невідома ознака — `null`.
Нові синоніми додавай до того самого ID. Бренди, магазини й вагу не додавай як
окремі варіанти. Назва чека сама по собі може бути неоднозначною; такі рядки
залишаються `review`, навіть якщо один із атрибутів відомий.

## Підготовка й перевірка

З кореня репозиторію:

```powershell
node scripts/product-taxonomy/prepare.mjs
node --test scripts/product-taxonomy/catalog-tools.test.mjs
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/product-taxonomy/verify-local.ps1 -VerifyBackfill
```

Локальна перевірка створює новий каталог у TEMP і нову PostgreSQL на вільному
loopback-порту. Вона застосовує залежні міграції та нову схему, виконує SQL
assertions, а з `-VerifyBackfill` двічі застосовує backfill до штучної копії всіх
назв. Сервер зупиняється у `finally`, файли лишаються для діагностики. Вона не
торкається live БД чи наявних локальних серверів. Auth представлений вузькими
тестовими функціями; реальний Supabase Auth/PostgREST потребує окремого smoke.

Для локальної генерації типів використано офіційний
`@supabase/postgrest-typegen@0.2.0` із `pg@8.16.3`, встановлені лише в
gitignored `.cache/taxonomy-typegen`:

```powershell
npm install --prefix .cache/taxonomy-typegen --no-save @supabase/postgrest-typegen@0.2.0 pg@8.16.3
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/product-taxonomy/verify-local.ps1 -GenerateTypes
node scripts/product-taxonomy/merge-local-types.mjs
```

Це реальна introspection PostgreSQL, а не ручне написання контракту.
`merge-local-types.mjs` оновлює лише декларації, що належать таксономії, і
відмовляється видаляти наявні колонки. Решта контракту походить із попередньої
генерації live схеми. Після дозволеного production застосування потрібна звичайна
повна регенерація `supabase gen types --linked` з UTF-8 без BOM.

## Застосування після погодження

1. Перевір migration history, актуальність inventory та diff. Підготуй schema
   migration з цієї гілки й окремо переглянь `proposed-backfill.sql`.
2. Застосуй schema migration до цільового Supabase тільки за дозволом. Вона
   створює довідники/RPC/колонки й перекладає відомі широкі категорії, але не
   класифікує покупки.
3. Застосуй перевірений `proposed-backfill.sql` транзакційно. Він додає словник і
   заповнює лише ще порожню класифікацію за точними нормалізованими назвами;
   не змінює суми, початкові назви й широкі категорії, не призначає `review` чи
   `excluded`, не змінює негативні/нульові рядки позицій чека.
4. Перевір кількості призначень, три мови, синоніми, реальний авторизований
   PostgREST-запит з `receipt:receipts!inner(...)`, усі фільтри та позначення
   викинутого. Перегенеруй повні типи, потім випускай вебкод.

Порядок важливий: новий вебкод використовує RPC. Публікація вебкоду до міграції
дасть явну помилку завантаження «Викинули».

Повторний запуск не перезаписує призначені класифікації. Для зміни вже
класифікованого товару потрібен окремий явний UPDATE з переглядом відповідних ID;
це дозволяє зберігати ручні уточнення. Новий невідомий SKU не отримує вигадану
класифікацію автоматично: додай перевірену відповідність у каталог. Покупки
вже класифікованого SKU успадковують її через trigger.
