# Чеки з Gmail через Apps Script в акаунті власника

Статус: accepted. Доповнює [ADR-0016](0016-durable-background-receipt-imports.md).

Чеки EDEKA, Marktkauf, замовлення Amazon, рахунки Anthropic, Google Play і Uber приходять
листами в мітку Gmail «Різні чеки». Їх треба автоматично додавати в стійкий фоновий імпорт.
Репозиторій публічний, тому доступ до пошти не може залежати від коду. Він налаштовується
для кожного користувача окремо через базу.

## Рішення

**Push, а не pull.** Google Apps Script у Google-акаунті власника раз на годину читає одну
мітку й надсилає нові листи в Edge Function `ingest-email-receipts`.

- **Права скрипта.** Скрипт використовує розширений сервіс Gmail зі scope `gmail.readonly`,
  `script.external_request` і `script.scriptapp`. `GmailApp` не підходить, бо вимагає
  повний доступ `https://mail.google.com/`.
- **Що зберігає застосунок.** OAuth-токенів Gmail у Supabase немає. Є лише випадковий
  ingest-токен користувача (256 біт). База зберігає тільки його SHA-256 хеш і останні
  чотири символи для інтерфейсу.
- **Альтернатива, яку відкинули.** Edge Function з OAuth refresh token (`gmail.readonly`).
  Gmail не має scope для однієї мітки. Тоді витік service-role ключа, токена CLI з CI,
  пароля бази чи Supabase-акаунта давав би читання всієї пошти, зокрема листів скидання
  пароля і 2FA. Крім того, у режимі Testing refresh token живе 7 днів, а restricted scope
  потребує верифікації застосунку.

Що дає витік ingest-токена: він дозволяє лише реєструвати листи в черзі імпорту. Тобто
фальшиві чеки, витрати на LLM і місце в Storage, і все це в межах лімітів нижче. Читати
токен нічого не може. Відкликається одним RPC.

## Що налаштовується в базі

Таблиця `email_import_sources`, один рядок на підключення:

- `owner_email`: власник підключення.
- `paid_by`: хто платив за чеки з цих листів.
- `import_after`: дата, з якої імпортувати листи.
- `allowed_sender_domains`: дозволені домени відправників; піддомени входять автоматично.
- `token_hash`: SHA-256 хеш ingest-токена.
- `revoked_at`: позначка відкликання.

Створення, зміна доменів, відкликання і «повторити пропущений лист» йдуть через RPC з
перевіркою `is_allowed_user()` і власника. Мітку Gmail задають у Script properties на
боці Google, не в базі. Так навіть зламана база не може розширити, які листи скрипт
надсилає.

## Обробка листа

1. **Новий лист.** Скрипт надсилає `op: pending` зі списком id листів мітки, сервер
   повертає ще не бачені. Далі для кожного (до 20 за запуск) скрипт надсилає `op: ingest`
   із сирим RFC 822 листом. Розбір MIME робиться на сервері (`postal-mime`), тож зміни
   парсерів не вимагають оновлювати скрипт у Google.
2. **Пропуск.** Лист реєструється як пропущений і не потрапляє до LLM, якщо:
   - він отриманий до `import_after`;
   - домен відправника не в `allowed_sender_domains`;
   - Gmail не записав DMARC pass або вирівняний DKIM pass. Береться лише перший заголовок
     `Authentication-Results` від `mx.google.com`; відправник може дописати фальшиві лише
     нижче.
   - він не має вмісту чека або його не вдалося розібрати.

   Перевірка домену потрібна, бо фільтр Gmail шукає підрядок у From. Перевірка DMARC
   потрібна, бо From можна підробити.
3. **Документи.** Кожне PDF-вкладення (за сигнатурою `%PDF-`, до 10 МБ, до 3 на лист)
   стає звичайним файлом імпорту. Лист без PDF стає текстовим документом `text/plain`:
   рядки From/Date (Europe/Berlin)/Subject, далі тіло. HTML перетворюється на текст
   лінійним проходом, бо функція має 2 с CPU. Провайдери отримують текст як документ;
   промпт для листів окремо каже ігнорувати інструкції всередині листа.
4. **Реєстрація.** `register_email_import_message` атомарно записує лист і файли в денний
   батч джерела (дата за Europe/Berlin) і ставить їх у PGMQ. Дублікати за вмістом
   отримують статус `duplicate` без об'єкта в Storage. Ліміт у 30 листів на добу
   перевіряється до завантаження в Storage і ще раз у транзакції.

## Наслідки

- **Видимість.** Журнал листів (відправник, тема) бачить лише власник підключення. Самі
  документи стають звичайними файлами імпорту й чеками і видимі всім користувачам з
  allowlist, як будь-який завантажений чек.
- **Що лишається поза імпортом.** Amazon надсилає підтвердження замовлення, а не чек.
  Скасування й повернення не імпортуються. Лист із кількома замовленнями без загальної
  суми йде на перевірку.
- **Текстові документи.** `text/plain` допустимий лише для шляхів `…/email/…`
  (`receipt_import_files_text_only_from_email`), тож браузерне завантаження не може
  зареєструвати текст.
- **Оновлення скрипта.** Код скрипта лежить у `tools/gmail-receipt-sync/`. Після його
  зміни власник вставляє новий код у свій проєкт Apps Script вручну.
- **Налаштування.** Інструкція: [docs/gmail-import.md](../gmail-import.md).
