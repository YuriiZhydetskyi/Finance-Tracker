# ADR-0007: Products як **необов'язковий** покажчик; селективний каталог

- Status: accepted
- Date: 2026-05-04

## Context and Problem Statement

Користувач хоче трекати ціни деяких регулярних товарів через магазини (наприклад, "Pesto Barilla 190g коштує 3.49 в Aldi/Lidl/Rewe, інколи на знижці 1.49"), але **не хоче** змушувати кожен item у чеку бути продуктом. Помідори, риба за вагою, одноразові покупки, варіативні товари — для них примусове створення Product призводить до брудних даних і втоми користувача.

## Considered Options

1. **Кожен Item обов'язково має Product** — AI завжди створює canonical entry.
2. **Items з product_id nullable** — Products є селективним каталогом тільки для канонічних регулярних товарів. AI повертає 3 результати: link / propose new / null.
3. **Без Products взагалі** — все агрегується по нормалізованій назві.

## Decision Outcome

Обрано **варіант 2** — Products як необов'язковий вимір.

`Items.product_id` — **nullable FK** на `Products.id`. Item з `product_id = null` валідний і повноцінний; просто не бере участі в product-level аналітиці (а category-level — бере, через `Items.category`).

### AI має 3 результати на item

1. **Лінк до існуючого** — впевнений матч (`existing_product_id`, confidence ≥ 0.8).
2. **Запропонувати новий** — товар явно канонічний (бренд + розмір/обсяг), варто додати в каталог (`proposed_canonical_name`).
3. **`product_id = null`** — товар не варто каталогувати.

User у review-UI бачить 3-state pill і може override будь-який варіант.

### Евристика для null (у промпті)

Не створювати Product, якщо:
- немає чіткого бренду ("помідори", "хліб");
- багато сортів/варіацій;
- ціна за вагу і одиниця змінна;
- очевидно одноразова покупка;
- назва занадто загальна.

Створювати Product, якщо:
- чіткий бренд + розмір ("Barilla Pesto 190g");
- регулярна повторювана покупка;
- стабільна ідентичність.

## Consequences

### Позитивні
- Базова аналітика (категорії, чеки, користувачі) працює без Products — ніщо не блокується.
- Ручне виправлення (merge duplicate products) не змінює історичні рядки `Items` — переписує тільки `product_id`.
- Каталог росте органічно і селективно — без брудних авто-створених entries.
- Користувач не пробивається через UI для кожного "помідор".

### Негативні
- Аналітика "де дешевше Coca Cola" працює тільки для каталогованих товарів. Для "помідорів" — не працює.
- AI має додаткову роботу в промпті: повертати `existing_product_id` / `proposed_canonical_name` / `null` + confidence. Більший response, складніша валідація.
- Ризик false-positive матчингу до неправильного existing Product. Мітигація: 3-state pill з override + майбутня сторінка `products.html` для merge duplicate.

### Майбутні фічі (out of MVP)
- **Promote item → product**: кнопка в `recent.html` / `edit.html` для перетворення раніше null-ового item на канонічний Product з можливим backfill схожих історичних items.
- **Products management page**: `products.html` для перейменування / merge / видалення (Phase 5).

## Pros and Cons of the Options

### 1. Кожен Item обов'язково має Product
- ✅ Однорідна модель, всі запити працюють однаково.
- ❌ Помідори → 50 канонічних "продуктів"; брудні дані; UI-тертя; AI вигадує canonical форми, які насправді не канонічні.

### 2. Nullable Products (обрано)
- ✅ Гнучкість, чистий каталог, fail-open.
- ❌ Аналітика на product-рівні охоплює лише підмножину items.

### 3. Без Products
- ✅ Найпростіше.
- ❌ Cross-store price tracking працює тільки через нормалізацію тексту — фрагільно ([ADR-0008 розглядає це окремо](0008-prices-computed-from-items.md)).
