# ADR-0025: Багатомовні сімейства та варіанти товарів

- Status: accepted
- Date: 2026-09-07

## Context and Problem Statement

Потрібно групувати покупки детальніше за поточні широкі категорії та знаходити
покупки у «Викинули» за українськими, англійськими й німецькими назвами. Каталог
ідентифікує магазинні товари за кодом або назвою; рядок чека може не мати зв'язку
з каталогом. Початкові назви чеків часто скорочені й мають залишитися історичним
свідченням. Вільний текст «Bio Barilla Penne 500 г» змішує різні виміри пошуку.

## Considered Options

1. Додати два довільні текстові поля: просто, але переклади, друкарські помилки й
   бренди створюють дублікати та некоректні пари сімейство/варіант.
2. Побудувати дерево довільної глибини: гнучко, але поточний запит потребує лише
   двох чітких рівнів; атрибути бренду й органічності все одно не є гілками дерева.
3. Два довідники зі стабільними ID, перекладами, синонімами й окремими атрибутами
   каталожного товару.

## Decision Outcome

Обрано варіант 3. Широка `category` залишається чинним виміром звітності.
`product_families` описує сімейства («Помідори», «Макарони», «Молоко»),
`product_variants` — конкретизацію всередині сімейства («Коктейльні», «Пенне»).
Варіант має рівно одного батька. Сімейство без відомого варіанта є валідним.

ID — стабільні англомовні `snake_case` ключі довідника, незалежні від перекладів.
Це виняток до ULID для транзакційних сутностей, подібний до природного ключа
наявного довідника категорій. Кожний запис має `name_uk`, `name_en`, `name_de` і
`aliases`: останні містять пошукові форми будь-якою з підтримуваних мов. Для
категорії наявна `name` є українською назвою, додаються англійська, німецька й
синоніми. Окремі колонки для трьох мов забезпечують повноту перекладів без
складнішого механізму довільних локалей; нова мова потребуватиме міграції.

`products` та `items` мають nullable `product_family_id` і `product_variant_id`.
Складений FK перевіряє, що варіант належить саме вказаному сімейству. Історична
позиція може отримати класифікацію навіть без `product_id`. Сімейство не прив'язане
FK до широкої категорії: джерело вже містить розбіжності категорій, виправлення
яких є окремим рішенням і не має блокувати класифікацію.

Бренд (`brand`), органічність (`is_organic`), одиниця й розмір упаковки належать
конкретному каталожному товару. За уточненим правилом користувача для впізнаваних
харчових товарів без Bio/organic ставимо `is_organic = false` як робоче припущення;
з явною позначкою — `true`. Для неоднозначних назв або незастосовної ознаки
лишаємо `null`. Це класифікація за наявною назвою, а не перевірка сертифіката.
Сімейства/варіанти придатні
для харчів, одягу, електроніки та послуг. Знижки й застава за тару можуть лишатися
без товарної класифікації.

### Історія та імпорти

При вставці позиції БД успадковує класифікацію пов'язаного продукту, якщо позиція
не містить явної класифікації. Це працює для ручного, інтерактивного й фонового
імпорту без дублювання логіки у різних runtime. Виправлення каталогу не переписує
історичні ID. Переклади та синоніми довідника виправляються для всіх покупок.

Від'єднання від каталогу зберігає класифікацію покупки; зміна зв'язку на інший
продукт успадковує нову, якщо не передано явне перевизначення. Редагування чека
видаляє й створює позиції заново: форма переносить класифікацію лише для
незмінених назви, коду, магазину й зв'язку з каталогом. Нова або перейменована
позиція проходить звичайне визначення продукту.

Пошук надає пріоритет класифікації позиції. Для старих некласифікованих позицій
дозволено fallback до поточного продукту. Якщо позиція має лише сімейство,
варіант з каталогу не підмішується. Бренд та органічність у цьому релізі беруться
з поточного каталогу, а не з історичних snapshot.

### Пошук та безпека

`search_waste_items(p_query)` повертає `setof items` з правами поточного
користувача (`security invoker`). Кожне слово запиту має міститися у сукупності
початкової назви, коду, бренду, перекладів і синонімів категорії/сімейства/варіанта.
Ураховуються регістр, діакритика, німецькі `ä/ae`, `ö/oe`, `ü/ue`, `ß/ss`.
`%` та `_` є буквальними символами. Повнотекстовий stemmer для однієї мови не
використовується: нерегулярні форми забезпечуються явними синонімами.

Feature API зберігає фільтри дати/магазину/ціни/категорії, отримує сторінки по 500
рядків з однозначним сортуванням та лише потім прибирає повністю списані позиції.
Нові таблиці мають explicit grants і RLS через `is_allowed_user()`.

## Consequences

- Пошук `яблуко`, `apple`, `Apfel` знаходить одну й ту саму класифіковану покупку.
- Первинний текст чеків, грошові суми та широкі категорії залишаються історичними.
- Класифікацію готує перевірюваний каталог; нечіткі назви не вгадуються. Новий
  невідомий продукт потребує поповнення словника/класифікації. Існуючий
  класифікований SKU автоматично передає класифікацію новим покупкам.
- Пошук перебирає відповідні рядки й словник у SQL. Для особистого журналу це
  свідомий простий вибір; при суттєвому зростанні даних індексований пошуковий
  документ треба обґрунтувати вимірюванням, а не вводити наперед.
- Перед вебрелізом необхідні schema migration і погоджений backfill. Перевірка
  на локальній PostgreSQL не доводить роботу deployed PostgREST/Auth.
