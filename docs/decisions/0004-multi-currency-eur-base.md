# ADR-0004: Multi-currency з EUR як базою; зберігаємо оригінал + EUR + курс

- Status: accepted (revised)
- Date: 2026-05-04
- Revised: 2026-05-04 — звужено скоуп до EUR + UAH; курси отримуються live з NBU при збереженні чеку, лист `FxRates` і інтеграція з ECB видалені (див. секцію Changelog внизу).

## Context and Problem Statement

Користувачі живуть у Берліні (валюта чеків — EUR), але інколи мають онлайн-покупки в гривнях. Потрібна можливість:
- Записувати витрати в оригінальній валюті.
- Аналізувати все в одній базовій валюті.
- Не переписувати історичні дані заднім числом, якщо центральні банки переглядають архівні курси.

## Considered Options

1. **Зберігати оригінал + EUR-нормалізація + курс на момент фіксації** (на Receipt-рівні; денормалізовано на Items).
2. Зберігати тільки оригінал, конвертувати в EUR при кожному запиті.
3. Зберігати тільки EUR (втрачаємо оригінал).

## Decision Outcome

Обрано **варіант 1** з такою деталізацією:

- Базова валюта — **EUR**.
- На `Receipts`: `currency`, `total_orig`, `fx_rate_eur`, `total_eur` (audit trail оригіналу + конвертація в EUR + курс на момент фіксації).
- На `Items`: `unit_price_orig`, `total_orig`, `total_eur` (денормалізація для аналітики без джойнів).
- Підтримуються **EUR (база) + UAH** (джерело: NBU). Інші валюти — out of scope; розширення — точкове через `Fx.getRateLive`.
- `fx_rate_eur` фіксується у Receipt при збереженні і ніколи не перераховується — навіть при редагуванні чеку зберігається той курс, який був на момент покупки.

### FX lookup — live, не persisted
Курс отримується **live** з NBU під час збереження чеку (`Fx.getRateLive(currency, date)`):
- Для EUR → одразу повертає `1.0` без жодного запиту.
- Для UAH → робить виклик NBU API на дату чеку (підтримуються історичні дати).
- Якщо NBU повертає порожньо (вихідний/свято) → walk-back до 7 днів назад, бере найближчий доступний курс.
- Результат записується в `Receipt.fx_rate_eur` як audit; **жодної окремої таблиці курсів немає**.

Чому без `FxRates` листа: у нас тільки одна не-базова валюта (UAH) і ~декілька-десятків UAH-чеків на рік. Підтримувати daily trigger + 90-day backfill + seed — більше складності, ніж користі. Live fetch при save — простіше, завжди свіже, без drift.

### Джерело курсу
- **NBU (bank.gov.ua)** — `?valcode=EUR&date=YYYYMMDD&json` повертає одну точку на запит. Підтримує історичні запити для будь-якої дати.
- ECB Reference Rates **не використовується** — він не покриває UAH (емпірично виявлено), а інші валюти нам не потрібні.

Альтернативи, відкинуті: матеріалізація через сторонні агрегатори (frankfurter.app, exchangerate-api) — додаткова залежність; зберігання курсів у листі — додаткова таблиця і trigger без переваг для нашого обсягу.

### Money precision rule
Грошові поля — `Number` з округленням до 2dp на write. `fx_rate_eur` — 6dp.
Реалізація: `Math.round(value * 100) / 100` у `Storage.js` перед записом у Sheet.

Чому не cents-integer (`349` замість `3.49`):
- Looker Studio і pivot-таблиці працюють із плаваючою точкою натурально.
- Дисплей-конверсію довелось би писати в кожному UI-місці.
- Sum/average формули в Sheet працюють напряму з floats.
- Rounding-on-write усуває drift на рівні I/O.

## Consequences

### Позитивні
- Аналітика на category-рівні і на product-рівні рахується у фіксованій базі — порівняння чесні.
- Історичні чеки не переписуються заднім числом — `fx_rate_eur` фіксований назавжди.
- Користувач бачить оригінал у деталях чеку, але дашборди — в EUR.
- Жодного daily trigger, жодної окремої таблиці курсів — менше рухомих частин.

### Негативні
- Дублювання `total_eur` на Items — додаткові ~10 байт на рядок. Ціна за відсутність джойнів у Looker.
- Floats: `0.1 + 0.2 = 0.30000000000000004`. Мітигація — rounding-on-write і round-on-display.
- Збереження UAH-чеку залежить від доступності NBU API в момент save. Якщо NBU лежить — save падає; користувач бачить помилку. Прийнятно для нашого обсягу (рідкісні UAH-витрати), але є точка відмови.
- Додавання нової валюти потребує точкової зміни `Fx.getRateLive` (не безкоштовно, як було б із загальним ECB-feed). Trade-off на користь простоти.

## Pros and Cons of the Options

### 1. Оригінал + EUR + курс (обрано)
- ✅ Історична правда, проста аналітика, одна точка ентропії.
- ❌ Більше колонок.

### 2. Тільки оригінал, конвертація при запиті
- ✅ Менше колонок.
- ❌ Кожен дашборд має робити lookup у `FxRates`; ризик показати "поточний" курс замість історичного.

### 3. Тільки EUR (втрачаємо оригінал)
- ✅ Найменше колонок.
- ❌ Незворотна втрата інформації; не зможемо показати чек у валюті, в якій його сплачували.

## Changelog

### 2026-05-04 — Звуження скоупу: EUR + UAH only, live fetch без зберігання курсів

**Що змінилось:**
- Видалено лист `FxRates` зі схеми.
- Видалено інтеграцію з ECB Reference Rates (`Fx._fetchEcbAndAppend`, `_parseEcbXml`, `Config.ECB_*_URL`).
- Видалено `Storage.appendFxRates` і `Storage.listFxRates`.
- Видалено daily time trigger (`Fx.refreshDaily`, `Fx.backfill90Days`, `Fx.installDailyTrigger`, `fxDailyTriggerHandler`).
- `Fx.getRate(currency, date)` перейменовано в `Fx.getRateLive(currency, date)`; тепер хоче live з NBU замість лукапу в листі.

**Чому:**
- Реальний скоуп — двоє людей у Берліні, EUR як основна валюта, рідкісні UAH-онлайн-витрати. Інші валюти ніколи не з'являлись у use-case.
- Зберігати курси для всього світу заради UAH — overengineering. Live-запит при збереженні чеку (~150 ms) простіший і завжди свіжий.
- Менше коду, менше тестів, менше документації, менше "як це підтримувати в Phase 5".

**Як живуть існуючі чеки:**
- Усі поля `Receipts` і `Items` (включно з `fx_rate_eur`, `total_orig`, `total_eur`) залишаються — це audit trail кожного чеку, не залежить від присутності `FxRates`.
- Якщо в `FxRates` лишаються старі рядки — їх можна вручну видалити (нічого від них не залежить).
