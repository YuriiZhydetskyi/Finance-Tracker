# Імпорт упаковок із JSON та сторінок PDF

Статус: accepted. Доповнює [ADR-0027](0027-packaged-product-catalogue.md).

Один PDF може містити чек і фото кількох товарів. Порядок товарів у відповіді ШІ
не визначає їхню відповідність позиціям чека. Новий імпорт приймає JSON із явними
номерами сторінок, показує JPEG для перевірки та записує тільки підтверджені
користувачем прив’язки. Схема наявних таблиць не змінюється.

## Контракт

```json
{
  "schema_version": 1,
  "receipt_pages": [1],
  "products": [
    {
      "name": "Pringles Original 165 г",
      "category": "Снеки",
      "barcode": null,
      "source_pages": [
        { "page": 2, "kind": "front" },
        { "page": 3, "kind": "back" }
      ],
      "receipt_matches": [
        {
          "store": "REWE",
          "receipt_label": "Originals",
          "store_product_code": null,
          "receipt_date": "2026-09-13",
          "receipt_page": 1
        }
      ]
    }
  ]
}
```

Нутрієнти та інші поля товару відповідають чинному `PackagedProductImportSchema`.
Повний приклад і правила транскрибування доступні кнопкою «Скопіювати запит» в
імпорті «Додати JSON + PDF». Скорочений приклад вище пояснює тільки зв’язки.

- Сторінки нумеруються від 1 від початку **того самого** PDF, включно з чеком.
- `receipt_pages` призначені лише для перегляду. Фінансовий чек цей імпорт не
  створює; його додають через наявний імпорт чеків.
- `source_pages` належать конкретному товару. Одна сторінка — один товар і один
  тип: `front`, `back`, `nutrition`, `ingredients`, `barcode`, `other`.
  Повтор сторінки чи використання сторінки чека як упаковки блокує імпорт.
  Якщо на звороті одночасно склад і таблиця, достатньо одного `back`.
- Колажі кількох товарів на сторінці треба рознести на окремі сторінки перед
  аналізом. Координати обрізання й автоматична сегментація не підтримуються.
- Сторінки без призначення перелічуються на перегляді й не зберігаються.
- JSON зі сторінками потребує PDF. Якщо PDF доданий, кожен товар має мати
  `source_pages`; порожні посилання не перетворюються на удаваний успіх.
- Старий JSON одного товару, масив або об’єкт `products` без посилань на
  сторінки залишається дозволеним. Це картки **без фото**.
- `receipt_matches` — підказки для ручного вибору. Вони не містять довірених ID
  і ніколи автоматично не змінюють FK. Збіг назви перевіряється в межах магазину.
  Один магазинний рядок не можна вибрати для двох карток в одній вставці.

## JPEG і збереження

PDF.js завантажується за потреби та рендерить сторінки послідовно в браузері:
білий фон, JPEG quality 0.92, довга сторона до 3000 px, збільшення до 4 разів.
Вбудований поворот PDF зберігається. Ліміти: 20 МБ PDF, 100 сторінок,
50 товарів і 100 МБ сумарних підготовлених JPEG. Кодеки, шрифти й worker
постачаються з тієї самої зафіксованої npm-версії на власному origin.
Нерозпізнані/пошкоджені чи захищені паролем документи відхиляються.

Файли упаковок записуються в чинний приватний bucket `packaging`, а їхні рядки —
у `packaged_product_photos`. `note` фіксує назву вихідного PDF, номер сторінки та
SHA-256. Для нових карток `raw_import_json` містить вихідний об’єкт і контекст PDF.
Сам PDF не архівується автоматично: користувач може додати його окремо в картку.

Точний наявний штрихкод, або нормалізована назва серед карток **без штрихкоду**,
дає змогу повторно використати картку. Перед збереженням це видно у перегляді;
її харчова цінність і назва не перезаписуються. Нові JPEG додаються до неї.
Це не нечітке об’єднання товарів лише за схожістю назв.

Storage і Data API не утворюють спільної транзакції. Імпорт послідовно створює
картку, зберігає всі потрібні фото, а потім прив’язує вибрані магазинні рядки.
Помилка залишає вже завершені кроки видимими. Перегляд утримує стабільні ID
карток до завершення, а ім’я JPEG включає SHA-256 PDF та номер сторінки.
Повтор після втраченої відповіді не дублює завершені кроки й не видаляє
файли, які вже могли бути записані. Змінена паралельно прив’язка не перетирається.

Незавершений план живе у вкладці браузера, а не у фоновій черзі. Після
перезавантаження сторінки треба повторно додати JSON/PDF: наявні картки буде
знайдено за їхньою ідентичністю; JPEG того самого PDF повторно не додаються
для того самого користувача й картки. При перериванні між Storage і записом
рядка може залишитись об’єкт без рядка; це наявне обмеження життєвого циклу Storage.

## Дата як підказка

Частота покупок лишається порядком черги. У перегляді доступні надрукована дата
чека з `receipt_matches` та дата останньої покупки кандидата. Жодна дата не
створює прив’язку автоматично.

Автоматичне зіставлення за EXIF чи близьким часом завантаження поки не
реалізоване. Для подальшого розширення треба окремо розрізняти дату зйомки,
дату покупки, експорт PDF і завантаження до програми. Справжня дата зйомки
може посилити підказку, але її відсутність або велика різниця не повинна
відхиляти збіг за ідентичністю. Не можна трактувати `File.lastModified`
або PDF `CreationDate` як достовірну дату фотографування.

Наявність картки й наявність фото — різні стани. Черга тепер називається
«Без картки»; у каталозі картки без файлів мають позначку «Фото ще не додано».

Рендерер спирається на [офіційний приклад PDF.js](https://mozilla.github.io/pdf.js/examples/),
а поведінка повторного завантаження — на
[контракт Supabase Storage](https://supabase.com/docs/guides/storage/uploads/standard-uploads).
