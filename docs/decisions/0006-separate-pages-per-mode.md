# ADR-0006: Окремі HTML-сторінки на кожен режим (photo / manual / edit) із спільними Alpine-компонентами

- Status: accepted
- Date: 2026-05-04

## Context and Problem Statement

Користувач має три способи створити/змінити запис:
- **Photo** — завантажити фото чеку, AI парсить, юзер ревьюить і зберігає.
- **Manual** — порожня форма для онлайн-витрат.
- **Edit** — завантажити існуючий чек з Sheet, змінити, зберегти.

Перша інтуїція — зробити один універсальний `review.html` з трьома режимами через query-параметр. Виглядає DRY: форма редагування item-списку однакова.

## Considered Options

1. **Один універсальний `review.html` з 3 режимами** (mode=photo / manual / edit).
2. **Три окремі HTML-сторінки** (`photo.html`, `manual.html`, `edit.html`) + **спільні Alpine-компоненти** для items table і summary.

## Decision Outcome

Обрано **варіант 2** — три окремі сторінки + спільні компоненти.

Структура:
```
src/ui/
├── photo.html      ← upload → parse → review
├── manual.html     ← порожня форма
├── edit.html       ← завантаження по ID
├── recent.html     ← список з лінками на edit
├── index.html      ← landing з 3 кнопками
└── shared/
    ├── ItemsTable.html   ← x-data компонент: редагування рядків
    ├── Summary.html      ← total + pie chart
    └── webapp.js         ← API клієнт (Promise wrapper над google.script.run)
```

DRY досягається через **компоненти**, не через колокацію режимів.

## Consequences

### Позитивні
- Кожна сторінка читається сама по собі без розгадування `mode === 'edit'` гілок.
- Photo-сторінка може еволюціонувати (додати "перепарсити з підказкою") без ризику зламати manual чи edit.
- Edit-сторінка може мати свої деталі (delete-кнопки, "повернути оригінал") локально.
- Зміна одного режиму — зміна одного файлу.
- DRY на рівні компонентів: items-table і summary — один раз, але не вся сторінка.

### Негативні
- Більше файлів (3 замість 1).
- Якщо логіка items-table змінюється — треба переконатись, що компонент справно працює в усіх 3 контекстах.

### Чому не "один файл з режимами"
Ми проаналізували реальну подібність трьох екранів і знайшли значущі розбіжності:

| Аспект | Photo | Manual | Edit |
|---|---|---|---|
| Початковий стан | Парс із Gemini, потенційно з помилками | Порожньо | Завантаження з Sheet за ID |
| Header | "Перевір розпізнане" + "Перепарсити" | "Новий онлайн-запис" | "Редагування від {date}" |
| Фокус UI | Review pre-populated | Швидке додавання | Обережне редагування |
| Save | INSERT | INSERT | UPDATE |
| Delete-кнопки | — | — | ✅ |
| Cancel поведінка | Викинути парс | Викинути ввід | Повернути оригінал |
| Error scenarios | "Не вдалось розпарсити" | Валідація форми | "Не знайшли запис" |

Об'єднати = ялинка з `if (mode === ...)` гілками. UI планується розвивати — об'єднана версія через рік стане непідтримуваною.

## Pros and Cons of the Options

### 1. Один універсальний review.html
- ✅ Менше файлів.
- ❌ Conditional logic скрізь, ризик "зламав один режим, фіксячи інший", еволюція ускладнюється.

### 2. Три окремі сторінки + shared components (обрано)
- ✅ Кожен файл читається ізольовано, режими еволюціонують незалежно, DRY через компоненти.
- ❌ Більше файлів; компонент має тестуватись у 3 контекстах.
